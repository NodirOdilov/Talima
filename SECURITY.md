# Политика безопасности проекта Talima 2.0

## 1. Область действия

Данный документ определяет порядок сообщения об уязвимостях, сроки реагирования и рекомендации по безопасной эксплуатации платформы Talima в производственной среде.

---

## 2. Поддерживаемые версии

| Ветка / релиз | Поддержка исправлений безопасности |
|---------------|-------------------------------------|
| `main` (активная разработка) | Да, приоритетно |
| Стабильные релизы с тегом | По мере возможности, в зависимости от критичности |

Рекомендуется использовать актуальное состояние ветки `main` или последний помеченный релиз.

---

## 3. Сообщение об уязвимости

Безопасность пользователей и данных — приоритет проекта. Если вы обнаружили уязвимость, **не создавайте** публичный Issue или Pull Request с описанием проблемы.

### Предпочтительные каналы

| Канал | Описание |
|-------|----------|
| [GitHub Security Advisories](https://github.com/NodirOdilov/Talima/security/advisories/new) | Приватный отчёт, рекомендуемый способ |
| [Nodir Odilov на GitHub](https://github.com/NodirOdilov) | Альтернативный канал при недоступности Advisories |

### Содержание отчёта

Для ускорения анализа укажите:

- Тип уязвимости (например: XSS, IDOR, обход авторизации, утечка данных).
- Затронутый компонент: `backend`, `frontend`, конкретный endpoint API.
- Пошаговые инструкции по воспроизведению.
- Оценку влияния (CVSS или текстовое описание последствий).
- Предложение по исправлению (при наличии).

## 4. Сроки реагирования

| Этап | Ориентировочный срок |
|------|----------------------|
| Подтверждение получения отчёта | 48 часов |
| Первичная оценка и классификация | 7 календарных дней |
| Разработка и выпуск исправления (критичные) | по согласованию с исследователем |
| Публикация security advisory | после выпуска патча |

Сроки могут корректироваться для сложных случаев; исследователь будет уведомлён о статусе.

---

## 5. Категории рисков

### Backend (Django / Django REST Framework)

- Обход аутентификации или авторизации (`RolePermission`, JWT).
- IDOR при доступе к чужим записям (`student`, `payment`, `message` и др.).
- Mass assignment через сериализаторы.
- SQL-инъекции при использовании сырого SQL вне ORM.
- Утечка `SECRET_KEY`, паролей или токенов в логах.

### Frontend (React)

- XSS при небезопасном рендеринге пользовательского ввода.
- Некорректная конфигурация CORS в production.
- Открытые редиректы в маршрутизации.
- Хранение JWT в `localStorage` (риск при успешной XSS-атаке).

### Инфраструктура

- `DEBUG=True` в production.
- Слабый или скомпрометированный `SECRET_KEY`.
- Публичный доступ к Django Admin без дополнительной защиты.
- Незащищённые экземпляры Redis или PostgreSQL.

## 6. Рекомендации для production

### Обязательные настройки

```env
DEBUG=False
SECRET_KEY=<криптостойкий-случайный-ключ>
ALLOWED_HOSTS=your-domain.com
CORS_ALLOWED_ORIGINS=https://your-domain.com
DATABASE_URL=postgres://<user>:<password>@<host>:5432/talima
```

### Дополнительные меры

| Мера | Описание |
|------|----------|
| HTTPS | Обязателен для API и SPA |
| Django Admin | Ограничить VPN, whitelist IP или отдельный поддомен |
| Зависимости | Регулярный `pip audit`, `npm audit` |
| Демо-учётные записи | Не использовать пароль `talima2026` в production |
| Резервное копирование | Плановое копирование PostgreSQL |
| Мониторинг | Алерты на `/api/health`, аномалии в логах |
