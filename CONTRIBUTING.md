## 1. Перед началом работы

### Порядок действий

1. Ознакомьтесь с [README.md](README.md) и [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
2. Создайте **fork** репозитория на GitHub.
3. Клонируйте fork локально:

   ```bash
   git clone https://github.com/<ваш-логин>/Talima.git
   cd Talima
   ```

4. Настройте окружение (см. раздел 2).
5. Создайте ветку от `main`:

   ```bash
   git checkout -b feature/краткое-описание-задачи
   ```

### Принципы вклада

| Принцип | Описание |
|---------|----------|
| Одна задача — один PR | Не объединяйте несвязанные изменения |
| Документация | Обновляйте docs при изменении API или поведения |
| Без секретов | Не коммитьте `.env`, ключи, `db.sqlite3` |
| Обратная совместимость | Избегайте ломающих изменений API v1 без согласования |

## 2. Настройка окружения

### Системные требования

| Компонент | Минимальная версия |
|-----------|-------------------|
| Node.js | 18 |
| Python | 3.12 |
| npm | 9 |
| Git | 2.x |

### Backend

```bash
cd backend
python -m venv .venv

# Windows
.venv\Scripts\activate

# Linux / macOS
source .venv/bin/activate

pip install -r requirements.txt
cp .env.example .env
python manage.py migrate
python manage.py seed_data
python manage.py runserver 8001
```

### Frontend

```bash
# из корня репозитория
npm install
cp .env.example .env
npm run dev
```

### Проверки перед отправкой PR

```bash
# Сборка и типизация
npm run build

# Линтинг frontend
npm run lint

# Backend (из каталога backend/)
pytest
black .
ruff check .
```

## 3. Стандарты кода

### Python (backend)

| Правило | Детали |
|---------|--------|
| Стиль | PEP 8, форматирование `black` |
| Комментарии | На русском языке, как в существующем коде |
| Модели | В соответствующем Django-приложении домена |
| API | Через `TalimaViewSet`, ответ `{ success, data }` |
| Миграции | Только `python manage.py makemigrations`, в коммите вместе с моделями |
| Права | `RolePermission` и `allowed_roles` для новых ViewSet |

### TypeScript (frontend)

| Правило | Детали |
|---------|--------|
| Типизация | Строгий режим, избегать `any` |
| Компоненты | Функциональные, хуки React |
| API | Только через `apiClient` |
| CRUD-страницы | `ResourceCrudPage` + запись в `resourceConfigs.ts` |
| i18n | Ключи в `src/assets/translate/uz.json`, `ru.json`, `en.json` |
| Стили | TailwindCSS, существующие UI-компоненты shadcn |

### Документация

- Изменения API — обновить `docs/ARCHITECTURE.md` и при необходимости README.
- Новые переменные окружения — описать в README и `.env.example`.

## 4. Ветки и коммиты

### Соглашение об именовании веток

| Префикс | Назначение | Пример |
|---------|------------|--------|
| `feature/` | Новая функциональность | `feature/crm-lead-export` |
| `fix/` | Исправление ошибки | `fix/auth-token-refresh` |
| `docs/` | Только документация | `docs/architecture-update` |
| `refactor/` | Рефакторинг без смены поведения | `refactor/api-client` |
| `test/` | Тесты | `test/academics-serializers` |

### Формат сообщений коммитов

Рекомендуется Conventional Commits на русском или английском:

```
тип(область): краткое описание в настоящем времени
```

**Типы:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`

**Примеры:**

```
feat(academics): добавить фильтр групп по преподавателю
fix(auth): исправить обновление refresh-токена
docs: актуализировать раздел API в ARCHITECTURE.md
```

## 5. Pull Request

### Чеклист автора

- [ ] `npm run build` завершается без ошибок
- [ ] `npm run lint` без критичных замечаний
- [ ] Добавлены миграции (если изменялись модели)
- [ ] Обновлена документация (если менялся контракт API)
- [ ] Секреты и `.env` не включены в коммит
- [ ] PR связан с Issue (`Closes #номер`)

### Структура описания PR

| Раздел | Содержание |
|--------|------------|
| Что сделано | Краткое описание изменений |
| Зачем | Бизнес- или техническая мотивация |
| Как проверить | Пошаговая инструкция для ревьюера |
| Скриншоты | Для изменений UI |

### Процесс ревью

Сопровождающий проверяет код, тесты и документацию. Ориентировочный срок ответа — несколько рабочих дней. Замечания устраняются в той же ветке до merge.

## 6. Сообщения об ошибках

Создайте [Issue](https://github.com/NodirOdilov/Talima/issues/new), выбрав шаблон «Сообщить об ошибке».

Укажите:

- Фактическое и ожидаемое поведение.
- Шаги воспроизведения.
- Окружение: ОС, версии Node.js и Python, браузер.
- Логи: traceback Django или консоль браузера.
- Скриншоты при ошибках интерфейса.

**Уязвимости безопасности** не публикуются в Issues — см. [SECURITY.md](SECURITY.md).

---

## 7. Предложения по функциональности

Перед крупной доработкой создайте Issue с меткой `enhancement`:

- Описание бизнес-задачи.
- Предлагаемое решение (опционально).
- Затронутые модули: `crm`, `academics`, `finance` и т.д.

Согласование архитектуры до написания кода снижает риск отклонения PR.
